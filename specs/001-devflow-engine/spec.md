**创建时间**: 2026-04-27
**状态**: 草稿

## 用户场景与测试 *(必填)*

### 用户故事 1 - 端到端研发流水线执行 (优先级: P1)

作为研发团队成员，我希望输入自然语言需求后，引擎能自动拆解需求、设计方案、生成代码并提交评审，以便我只需在关键节点进行确认，从而极大提升研发效率。

**优先级原因**: 这是平台最核心的价值主张，验证了 Pipeline 引擎和 Agent 编排的基础能力，是整个产品跑通的基础。

**独立测试**: 可以通过配置一个包含“需求分析”、“方案设计”和“代码生成”三个阶段的流水线，并输入一个简单的需求，观察系统是否能自动流转并产出对应的代码文件进行验证。

**验收场景**:

1. **给定** 引擎已部署且配置了包含需求分析和代码生成的流水线，**当** 用户提交“增加一个用户登录功能”的自然语言需求时，**那么** 引擎自动启动 Pipeline，按序调用对应的 Agent 生成结构化需求和代码，并在配置的人工检查点暂停等待确认。
2. **给定** Pipeline 运行到“方案设计”的人工检查点，**当** 用户在界面上点击“Reject”并附带理由“缺少安全性考虑”时，**那么** 引擎自动将状态回退到上一节点（或重新执行当前节点），Agent 结合 Reject 理由重新输出方案。
3. **给定** Pipeline 完成所有自动和人工确认阶段，**当** 流程结束时，**那么** 引擎输出可合并的代码变更集（Diff）或直接生成 PR/MR。

---

### 用户故事 2 - 网页端“所见即所得”的修改与预览 (优先级: P1)

作为产品或设计人员，我希望在目标网页上直接圈选元素并用自然语言下达修改指令，系统能实时修改代码并刷新预览，以便直观且快速地验证设计和需求。

**优先级原因**: 这是显著区别于传统研发的创新交互模式，极大降低了沟通成本，提供了极致的用户体验。

**独立测试**: 可以通过在测试网页注入悬浮控件，圈选某个按钮并输入“把这个按钮变成红色”，验证代码是否被自动修改且页面无刷新预览是否生效。

**验收场景**:

1. **给定** 浏览器已加载注入了 AI 悬浮控件的目标网页，**当** 用户使用鼠标圈选页面上的标题元素并输入“修改为欢迎来到我的网站”时，**那么** Agent 能够准确定位源代码中的对应位置并完成修改。
2. **给定** Agent 完成了代码修改，**当** 修改保存后，**那么** 网页通过热更新机制立即展示修改后的效果，无需用户手动刷新。
3. **给定** 用户对预览效果满意，**当** 用户点击“确认并提交”时，**那么** 系统自动生成包含修改摘要的 MR（Merge Request）。

---

### 边界情况

- 当用户输入的自然语言需求过于简短或模糊，导致 Agent 无法解析时会发生什么？
  - 系统（需求分析 Agent）应在当前节点向用户发起澄清提问，挂起 Pipeline 直到获取足够信息。
- 系统如何处理目标代码库过大，超出单次请求上下文限制（Token Limit）的场景？
  - 系统应实现代码库的按需检索或分块读取，Agent 仅加载与当前任务相关的文件上下文。
- 当热更新预览失败或代码修改导致编译错误时会发生什么？
  - 悬浮控件应向用户展示错误提示（而非直接崩溃），并提供一键回滚代码或要求 Agent 修复的选项。

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统必须提供一个可配置的 Pipeline 引擎，支持串行定义研发阶段（如需求、设计、编码、测试、评审）。
- **FR-002**: 系统必须支持为每个流水线阶段绑定具有特定 System Prompt 和角色的 AI Agent。
- **FR-003**: 阶段之间必须支持结构化数据的流转，即前一阶段的输出自动作为下一阶段的上下文。
- **FR-004**: 系统必须支持在 Pipeline 中配置人工检查点（Human-in-the-Loop），允许用户执行 Approve 或 Reject 操作。
- **FR-005**: 引擎必须提供 RESTful API 以管理 Pipeline 的生命周期（创建、启动、暂停、终止）和查询状态。
- **FR-006**: 引擎需支持配置多种 LLM Provider（如 OpenAI, Gemini, 阿里千问等）。
- **FR-007**: 系统必须包含一个前端页面应用（SPA），提供 Pipeline 可视化展示和操作入口。
- **FR-008**: 系统必须提供页面注入脚本或浏览器扩展，支持在目标页面展示悬浮交互框。
- **FR-009**: 注入脚本必须支持用户圈选页面上的 DOM 元素，并提取其上下文供 Agent 定位源码。
- **FR-010**: 系统必须能够基于前端构建工具（如 Vite/Webpack）实现代码修改后的热更新（HMR）预览。

### 关键实体

- **Pipeline**: 表示一次完整的研发流水线实例，包含状态、当前执行阶段、全局上下文信息。
- **Stage (阶段)**: Pipeline 中的单个执行环节，定义了输入输出契约、绑定的 Agent 及是否需要人工介入。
- **Agent**: 封装了 LLM 调用的执行单元，包含角色设定（Prompt）、工具列表和上下文感知能力。
- **Checkpoint (检查点)**: 需要人工决策的阻塞节点，记录用户的决策（Approve/Reject）及反馈意见。

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 平台能够完整无中断地执行“需求->设计->代码->测试->评审->交付”的六阶段完整流水线，并且 80% 的常规功能需求能生成可通过编译的代码及通过的单元测试。
- **SC-002**: 人工检查点（Approve/Reject）操作响应时间在 2 秒以内，且状态扭转准确无误。
- **SC-003**: 页面圈选交互中，Agent 能够从用户选取的 DOM 元素 100% 准确映射到对应的前端源代码文件及代码行。
- **SC-004**: 通过注入脚本修改代码后，热更新（HMR）生效的延迟不超过 3 秒。
- **SC-005**: 提供至少两种不同的主流模型（例如 GPT-4o 和 Gemini 1.5 Pro）的切换配置支持。

## 假设

- 用户提供的目标代码库使用的是主流前端技术栈（如 React + TypeScript），以便于实现准确的源码映射和热更新。
- 目标开发环境允许暴露文件系统操作 API 给 Agent 或服务端进程进行代码修改。
- 相关的代码仓库已由 Git 管理，并且运行环境已配置好与 Git 宿主（如 GitLab/GitHub）交互的认证凭据。
- 圈选功能的实现假设目标代码在开发模式下包含必要的 SourceMap 或 React DevTools 注入的数据属性以协助定位源码。
