# 研究决策: 工具调用式渐进探索 Agent

## 决策 1: 默认只要求用户提供仓库根目录

**决策**: 常规入口只要求 `rootPath`，`includePaths`、`excludePaths`、目标文件、预算参数全部作为高级选项。

**原因**: 赛题要求至少支持目录/文件路径提供上下文，但并不要求用户手动列出完整范围。对新需求分析来说，强制用户给 include/exclude 会把“代码感知”的责任转移给用户，体验上也不符合 Codex/Claude Code 的渐进探索范式。

**替代方案**:

- 路径驱动一次性聚合：实现简单，但容易漏掉相关文件或读取大量无关代码。
- Elasticsearch/向量混合检索：召回能力强，但引入额外基础设施、索引生命周期和测试成本，不适合作为 T019 基础能力的第一实现。

## 决策 2: 使用“规划-工具调用-反思”的短循环

**决策**: RequirementAgent 在需求分析开始后执行有限轮次循环：

1. 根据需求生成探索计划和候选关键词。
2. 调用文件发现工具获取目录轮廓。
3. 调用文本搜索工具定位候选模块。
4. 调用范围读取工具读取关键文件片段。
5. 归纳证据、更新置信度和缺口。
6. 若证据不足且预算未耗尽，继续下一轮；否则输出结构化上下文摘要。

**原因**: 该方式把状态判断交给 Agent，把工具执行限制在可审计工具内。它能像真实 coding agent 一样逐步披露上下文，同时避免一次性把整个仓库塞进提示词。

**替代方案**:

- 由 Temporal 维护每个文件读取状态：Temporal 适合维护长事务和检查点，不适合承载细粒度推理状态。
- 由 LangGraph 外部普通函数完成循环：可行，但 LangGraph 更适合表达节点状态、条件路由和工具调用边界。

## 决策 3: 检索主路径采用本地工具混合策略

**决策**: 第一版检索由本地工具组合完成：目录扫描、文件名匹配、后缀过滤、关键词搜索、符号/测试文件启发式、范围读取。输出 EvidenceItem，而不是无来源的摘要。

**原因**: 当前系统已经运行在本地执行平面，可以直接访问用户指定路径。本地工具不依赖索引服务，便于在测试环境和用户机器上复现。

**替代方案**:

- 向量检索：适合语义召回，但需要 chunk、embedding、索引更新和密钥配置。
- Elasticsearch BM25 + 向量混合：适合大规模企业代码库，但超出当前任务的基础能力范围。

## 决策 4: include/exclude 作为高级约束

**决策**: `includePaths` 默认等价于仓库根；`excludePaths` 默认包含 `.git`、依赖目录、构建产物、缓存、日志、虚拟环境和密钥类文件。用户显式传入 include/exclude 时，只改变探索边界和优先级，不改变 Agent 的渐进探索流程。

**原因**: 默认自动探索可以降低使用门槛；高级选项仍能满足隐私保护、性能控制和聚焦子模块的需求。

## 决策 5: 中间产物落在阶段输出和 trace

**决策**: 探索轨迹、LLM 消息和 EvidenceItem 通过现有 Stage 输出和 LLM trace 文件展示/存储；控制平面 API 返回当前阶段输出，前端展示探索摘要、已读文件、搜索词、证据和预算消耗。

**原因**: 项目已有 Pipeline/Stage 模型和 LLM trace 能力，不需要为 T019 升级新增表迁移。若后续需要独立查询中间产物，再扩展数据库模型。

## 决策 6: 预算与降级策略

**决策**: 默认配置包含最大轮次、最大读取文件数、最大读取字节数、单文件片段长度和最大搜索结果数。预算耗尽时输出 `DEGRADED` 上下文摘要，明确说明已检查内容、未覆盖范围和建议用户补充的路径。

**原因**: 自动探索必须可控，不能无限读取仓库。降级输出比失败更适合需求分析场景。

## 决策 7: 安全边界

**决策**: 所有路径先规范化再校验，必须位于 `rootPath` 内；符号链接、二进制文件、超大文件、密钥文件按策略跳过；trace 中不记录疑似密钥原文。

**原因**: 代码感知会读取用户本地文件，必须把权限边界定义在工具层，不能只依赖提示词约束。
