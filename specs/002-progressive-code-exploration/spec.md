# 功能规范: 渐进式代码库探索 Agent

**功能分支**: `002-progressive-code-exploration`  
**创建时间**: 2026-05-04  
**状态**: 草稿  
**输入**: 用户描述: "把 T019 的路径驱动工具升级为工具调用式渐进探索 Agent。不需要用户手写 include/exclude；include/exclude 变成高级选项，只在用户想限制范围、提升速度、保护隐私时使用。根据我们上文讨论的设计，进行升级。"

## 用户场景与测试 *(必填)*

### 用户故事 1 - 仅提供代码库根目录即可完成需求分析 (优先级: P1)

用户提出一个新需求时，只需要选择或填写目标代码库根目录。系统应自动识别候选文件、逐步读取相关代码、形成证据，并产出可追溯的结构化需求分析结果，而不要求用户手写包含路径或排除路径。

**优先级原因**: 这是本功能的核心价值。它降低用户使用门槛，使代码感知过程接近 Codex/Claude Code 的自然体验。

**独立测试**: 使用一个只包含需求文本和代码库根目录的请求启动需求分析，验证系统能读取相关文件、生成证据列表和结构化需求产物。

**验收场景**:

1. **给定** 用户只提供需求文本和代码库根目录，**当** 用户启动需求分析，**那么** 系统会自动探索代码库并返回包含已检查文件、选择理由和需求分析结果的产物。
2. **给定** 代码库包含依赖目录、构建产物和日志目录，**当** 系统自动探索，**那么** 这些常见无关目录默认不会进入候选文件集合。
3. **给定** 需求中出现业务关键词，**当** 系统探索代码库，**那么** 读取的文件应与这些关键词或相关模块有明确关联。

---

### 用户故事 2 - 高级用户可限制探索范围 (优先级: P2)

高级用户可以在需要时填写包含路径、排除路径、目标文件、文件数量上限和字节预算，用于限制范围、提升速度或保护敏感目录。系统应把这些限制视为边界条件，而不是普通用户必须填写的前置条件。

**优先级原因**: 自动探索需要安全边界和效率控制。高级约束让用户在大型仓库或隐私敏感场景中仍能控制 Agent 的行为。

**独立测试**: 使用相同需求分别运行默认探索和带高级约束的探索，验证约束后的探索只读取允许范围内的文件，并且仍能生成需求分析产物。

**验收场景**:

1. **给定** 用户设置了排除路径，**当** 系统探索代码库，**那么** 排除路径下的文件不会被读取、搜索或进入证据列表。
2. **给定** 用户设置了目标文件，**当** 系统探索代码库，**那么** 系统会优先评估目标文件，但仍可在预算内寻找其他相关文件。
3. **给定** 用户设置了较小的读取预算，**当** 系统探索大型代码库，**那么** 系统会在预算耗尽前停止，并在产物中说明受预算影响的范围。

---

### 用户故事 3 - 用户可审查探索过程和证据 (优先级: P3)

用户需要理解 Agent 为什么读取某些文件、哪些文件支持了需求分析结论、哪些信息仍不确定。系统应展示逐步探索记录和证据摘要，帮助用户判断结果可信度。

**优先级原因**: 自动代码感知如果不可解释，用户难以信任需求分析结果。可追溯记录也便于调试 Agent 行为。

**独立测试**: 对一次需求分析结果检查探索记录，验证每个关键结论至少能关联到需求文本、已读文件或明确的未确认问题。

**验收场景**:

1. **给定** 系统完成需求分析，**当** 用户查看中间产物，**那么** 用户能看到搜索词、读取文件、读取原因和证据摘要。
2. **给定** 系统无法确认某个需求细节，**当** 需求分析完成，**那么** 未确认问题会出现在结果中，而不是被系统编造。
3. **给定** 用户调整高级约束后重新运行，**当** 新结果生成，**那么** 用户能区分新旧探索记录及其证据差异。

---

### 边界情况

- 当用户没有提供代码库根目录时，系统应只基于需求文本生成分析，并明确说明未使用代码库上下文。
- 当代码库根目录不存在、不可访问或不是目录时，系统应给出可理解错误，并允许用户修正路径后重试。
- 当自动探索没有找到相关文件时，系统应返回低置信度结果和建议用户提供目标文件或范围约束。
- 当仓库非常大时，系统应遵守默认预算并优先读取高相关文件，而不是无差别遍历全部内容。
- 当文件不可读、为二进制文件或过大时，系统应跳过或截断，并在探索记录中说明。
- 当用户提供的高级约束相互冲突时，系统应优先保护排除路径和根目录边界。

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统必须支持用户仅提供需求文本和代码库根目录即可启动代码感知需求分析。
- **FR-002**: 系统必须将包含路径、排除路径、目标文件和读取预算作为高级选项，而不是普通用户必须填写的字段。
- **FR-003**: 系统必须在未提供包含路径时自动发现候选文件，并默认跳过常见依赖目录、构建产物、版本控制目录、虚拟环境目录和日志目录。
- **FR-004**: 系统必须采用逐步探索流程，先形成探索计划，再按相关性读取少量文件，并根据已获信息决定是否继续探索。
- **FR-005**: 系统必须记录每次探索动作的目的、输入、命中文件、读取文件和结果摘要。
- **FR-006**: 系统必须保证所有读取行为都限制在用户提供的代码库根目录内。
- **FR-007**: 系统必须严格遵守用户设置的排除路径，排除范围内的文件不得被搜索、读取或写入证据。
- **FR-008**: 系统必须在用户设置目标文件时优先评估目标文件，同时允许在预算内补充探索其他相关文件。
- **FR-009**: 系统必须为每次需求分析产出代码上下文摘要，至少包含已检查文件、搜索词、证据摘要、预算使用情况和置信度。
- **FR-010**: 系统必须把代码上下文摘要写入需求分析阶段产物，以便控制台或后续阶段展示。
- **FR-011**: 系统必须在信息不足时生成明确的开放问题，而不是用猜测填补关键需求。
- **FR-012**: 系统必须支持用户在一次探索后调整高级约束并重新运行，且新结果应反映新的探索范围。
- **FR-013**: 系统必须对不可读文件、二进制文件、超大文件和路径错误提供可审计的跳过说明。
- **FR-014**: 系统必须提供默认预算，防止单次需求分析读取过多文件或文本。

### 关键实体

- **代码库上下文请求**: 用户为一次需求分析提供的代码库根目录和可选高级约束。
- **探索会话**: 一次需求分析中的代码感知过程，包含探索计划、步骤、预算和结果。
- **探索步骤**: 系统为寻找上下文执行的一次搜索、列举、读取或摘要动作。
- **证据项**: 支持需求分析结论的文件、片段、摘要或未确认问题。
- **高级约束**: 用户用于限制范围、提升速度或保护隐私的包含路径、排除路径、目标文件和预算设置。
- **代码上下文摘要**: 面向用户和后续阶段的可展示产物，说明系统读取了什么、为什么读取、发现了什么和还缺什么。

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 在一个中等规模项目中，用户只提供需求文本和代码库根目录时，系统能在 2 分钟内生成包含代码证据的需求分析结果。
- **SC-002**: 对 10 个代表性需求进行测试时，至少 8 个结果能包含 3 个或以上与需求相关的已检查文件。
- **SC-003**: 对设置了排除路径的测试用例，100% 的结果不得包含被排除范围内的文件。
- **SC-004**: 对信息不足的需求，100% 的结果应包含开放问题或低置信度说明，而不是无依据地补全关键事实。
- **SC-005**: 在默认设置下，单次分析读取的文件数和文本量均不得超过系统声明的默认预算。
- **SC-006**: 80% 的首次使用用户无需填写包含路径或排除路径即可完成一次代码感知需求分析。

## 假设

- 用户至少能够提供目标代码库根目录；若未提供，系统仍可退化为纯需求文本分析。
- 默认排除规则覆盖常见依赖目录、构建产物、版本控制目录、虚拟环境目录、日志目录和临时目录。
- 需求分析阶段只读取代码和文档，不修改目标代码库。
- 自动探索优先服务于需求分析，不要求一次性建立完整代码索引。
- 高级约束的主要目的包括保护隐私、控制预算和缩短执行时间。
